  The spec's invariants are encoded as constraints rather than left to
  application code:

  - Cross-namespace sub-agents are unrepresentable (§13.3) —
    agent_version_sub_agents FKs on the composite (id, namespace_id) of both
    parent version and child agent, so the only way to reach another namespace
    is agent_version_peers.
  - Effect contracts live on the binding, not the tool (§8.3) — the same tool
    can be read_only for one agent and approval-gated for another. CHECKs make
    "never cache side-effecting operations", "idempotent requires a key" and
    "compensatable requires a named inverse" structural.
  - Leases split from runs into run_queue so heartbeat writes don't churn a
    40-column row.
  - interactions carries two run FKs — raised by the deepest run, answered up
    the chain (§14.3).
  - No cache tables, no A2A task table, no MCP session table, no business state
    — each absence is documented inline with its section ref.

  db/ERD.md — three mermaid ER diagrams (execution spine, control plane,
  state/memory/lineage), a table explaining the twelve load-bearing
  relationships and why each is shaped that way, and the partitioning section.

  One tradeoff I'd flag rather than bury: events is PARTITION BY RANGE

  Decisions worth flagging, since they shape the surface rather than just
  populate it:

  - sync/stream/async are delivery modes on the same routes, not separate ones
    (§18.4). There is no /v1/runs/stream — mode is a parameter, and every
    execution route is durable regardless.
  - A conversational turn is POST /v1/threads/{id}/runs, not a message endpoint.
    §12.1 makes client→server a plain POST; a turn is a new run on an existing
    thread, which is exactly what the thread/run split in the schema encodes.
  - GET /v1/runs/{id} is the async polling mode. No separate poll route.
  - Four absences are structural, not omissions — no MCP session routes (the
    protocol went stateless in the 2026-07-28 revision), no A2A task store

    declared per tool contract), no WebSocket control plane. Each is listed at
    the bottom with its section ref so a reader doesn't "fix" them later.

⏺ Two docs in ai-docs/plans/:

  lld.md — the design. Fourteen sections: process topology, module architecture,
  layering enforcement, directory layout, persistence, request context, nine
  core mechanisms worked out in SQL and pseudocode, error taxonomy,
  observability, testing, config, build order, deviations, open decisions.

  phase-0.md — the walking skeleton as an executable checklist with per-task
  exit criteria.

  The decisions that actually shape the build:

  Three deployables, not one. §2.3 requires workers to fail independently of the
  API. The scheduler is separate from the worker because its jobs are
  singleton-by-nature — reclaiming another worker's expired lease on N replicas
  is N races where one is correct. Leader election via pg_try_advisory_lock, no
  new dependency.

  advance() returns one step, not a run. This is the central choice at the
  framework boundary. A framework that runs to completion — as deepagents'
  invoke() does — gets wrapped with its callback stream translated into steps.
  That's exactly what consumer 01's AgentTracer already does, which is why that
  code is the model for the adapter rather than something to replace.

  The echo adapter ships in Phase 1, not later. §0.3 mandates a second
  orchestration adapter from the first release as the leak test. ~150 lines,
  fastest test in the suite, and the only thing that catches a deepagents
  concept seeping into steps or events. Paired with a tsconfig.core.json CI job
  that compiles the core with all adapters excluded — that turns §2.1's "must
  compile with every protocol adapter removed" from a principle into a red
  build.

  No ORM. The schema's CHECK constraints are the business rules — §8.3's caching
  rule, §13.3's namespace rule. Kysely with types generated from the live
  schema, so a migration that drops a column breaks the build.

  Two things I'd push back on, flagged rather than buried:

  1. Fencing needs a schema change I don't have. run_queue.lease_epoch isn't in
  db/schema.sql and must be. Heartbeats don't prevent split-brain — a worker
  stalled in GC loses its lease, worker B claims the run, and worker A wakes up
  and writes a step into a run it no longer owns. Two workers, one event log,
  two interleaved realities. Every durable write has to assert lease_owner = $me
  AND lease_epoch = $myEpoch in the same statement; zero rows affected means
  abandon locally. Section 7.2 has the SQL.

  2. §12.1's "HTTP/2 end-to-end" is stronger than its own stated reason. The
  rationale given is the ~6-connections-per-origin limit hanging streams on a
  third tab — that's a browser-to-edge constraint. Terminating HTTP/2 at the
  ingress and speaking HTTP/1.1 upstream satisfies it fully and keeps the
  Express adapter already in package.json. If you want end-to-end HTTP/2 for a
  reason beyond the one written down, the change is the Fastify adapter and it's
  cheaper now than later. I flagged it rather than deciding it.

  The one rule I'd protect above all others is in §7.6: a resumed run that finds
  its own non_idempotent invocation still marked running does not know whether
  the side effect happened. It may not retry and may not assume success — it
  marks the invocation indeterminate and either fails or raises an approval
  interaction. Three lines of code, and the difference between §4.5 being honest
  and being a claim.

  Milestone 4 is what I'd protect in the schedule: a durable run end-to-end on a
  fake framework, early. Everything after it becomes a change to a working
  system rather than a step toward a hypothetical one.

⏺ Short answer: no for streaming, yes eventually for analytics — and they're
  different problems that happen to share one table.

  Why LSM is wrong for the streaming path

  Three reasons, and the first is fatal:

  The transactional co-write is the guarantee. §4.5 rests on the event being
  appended in the same transaction as the state change it records — that's what
  makes a crash between "the run completed" and "the event exists" impossible.
  No external store can join that transaction. The workaround is an outbox,
  which makes the event log eventually consistent with the state it describes.
  An event log that can lag its own subject isn't a system of record, and §0.2's
  replay guarantee goes with it.

  Ordering comes from a row lock. UPDATE runs SET last_event_seq =
  last_event_seq + 1 ... RETURNING serialises allocation per run.
  Cassandra/Scylla have no cross-row transaction to hang that on — you'd need an
  external sequencer, which is a consensus problem you don't currently have.

  Push, not poll. LISTEN/NOTIFY wakes an SSE subscriber the instant an event
  commits. ClickHouse has no push primitive, so streaming becomes polling —
  adding latency to the one path that exists to be fast. And ClickHouse wants
  batched inserts, which directly contradicts "notify the subscriber now."

  Writes aren't the bottleneck anyway

  ~20 events/run. At 1M runs/day that's 230 inserts/sec — a single Postgres node
  doesn't notice. The real constraint is retention × analytics: 20M/day × 90
  days ≈ 1.8B rows, and the seq scan above is linear in that. So the trigger to
  act is analytical query latency, not write volume — and that distinction picks
  the solution.

  The cheapest correct step is already installed

  Your Postgres image carries TimescaleDB and timescaledb_toolkit. Hypertables
  on events and usage_ledger give time-chunking, native columnar compression
  (typically 10–20×) and continuous aggregates — inside Postgres, so the
  transactional co-write, the row lock and LISTEN/NOTIFY all survive untouched.
  That solves the analytics problem without introducing a datastore, meaning
  §11.3's "written justification" bar never has to be cleared.

  A columnar store belongs later as a derived projection, not a replacement.
  §13.4's "a second event store means the design has gone wrong" is about a
  second source of truth — a projection is ordinary CQRS.

  Written up as ai-docs/decisions/0001-event-storage.md, including what I
  rejected (dual-write is the exact shape §13.4 warns about) and four concrete
  revisit triggers.

  One caveat I'd flag: the honest failure mode isn't volume, it's per-run event
  count exploding — voice frames or thousand-step coding runs. The fix there is
  not a bigger log; it's §4.3's relaxed tier batching, because per-frame media
  events don't belong in an audit log at all.

  Same split as ADR 0001: Postgres for transactional/operational, columnar for
  high-volume time-series, blob for large payloads. Their blob carve-out is our
  §11.2 artifact carve-out, for the same reason — big content doesn't belong in

  But the roles differ, and that's the whole point

  LangSmith is an observability sink. Our event log is the execution system of
  record.

  A LangSmith trace is a read-only record of something that already happened
  somewhere else. If a trace is dropped, delayed, or batched, the application it
  describes is unaffected — nothing downstream resumes from it. That's
  precisely why they can afford ClickHouse as the primary trace store, and why
  the Redis queue in front of it is fine: async, batched, lossy-under-failure
  ingest is an acceptable tradeoff for telemetry.

  Our events table can't take that deal. It's what a crashed run resumes from,
  what Last-Event-ID streams from, and what replay reconstructs state from. That
  forces the three constraints in the ADR — transactional co-write with the
  state change, per-run ordering from a row lock, and LISTEN/NOTIFY push.
  LangSmith has none of those constraints because it isn't in anyone's recovery
  path.

  So their architecture is right for them and would be wrong for us — not
  because ClickHouse is worse, but because we'd be putting a recovery-critical
  log behind a batching queue.

  The convergence is still useful validation: when we add analytics, the shape
  LangSmith already landed on is the shape to copy — columnar as a projection,
  Postgres as the operational store, blob for payloads.

  Your question answered in code

  You asked "skills and knowledge base — or is it same like vector search?" The
  answer is half, and the design encodes which half:

  - Retrieval is the same. Knowledge chunks and semantic memories go through the
    same Embedder, the same cosine distance, the same 768 dimensions. I moved
    EMBEDDING_DIMENSIONS onto the port so a second index can't quietly acquire a
    second embedding contract.
  - Lifecycle is not. A memory is learned by a run, decays, is superseded,
    belongs to one tenant. A knowledge chunk is authored, replaced when its
    document is re-ingested, deleted when the document is, and shared by the
    whole namespace. Putting them in one table would have meant a superseded_by
    that never fires and no way to answer "which document did this come from" —
    the first question anyone asks of a KB.

  Skills are a third thing: versioned procedural content, not memory at all.

  Why skills had to be a registry

  A skill can carry tools. If skills were mutable text bound by name, editing
  one would change the behaviour and the authority of every published agent
  referencing it — no new spec hash, no admission decision, no record of who
  approved the widening. So publishing mints an immutable version, an agent pins
  the version, and deprecation stops new selections without breaking existing
  pins.

  The concrete attack this closes:

  { tools: ["payments.refund"] }     → refused, no grant
  { skills: ["refund-helper"] }      → would have worked

  Admission now takes the union of named tools and skill-borne tools before
  intersecting with grants, and names the skill in the rejection — "no grant for
  payments.refund" is baffling to an author whose spec never mentioned it.

  delegation — the two differ in every row of §13.3's table. Sub-agents resolve

  peers resolve across the org. A peer gets its own thread, its failure is
  contained by default, and it may not be in this runtime at all.

  is written once and executed against a local peer and a real loopback

  This is the piece that makes §0.5 enforceable rather than aspirational.
  Everything shipped in the last several batches — memory, compaction, skills,
  knowledge, cache, sub-agents, peers — is a compensating mechanism the spec
  says must justify itself or be removed. Until now none could be measured.

  The A/B, and the one decision that matters

  A suite names mechanism_under_test. The runner executes the version as
  published, then flips one spec field, puts that variant through admission,
  materialises it as its own agent version, and runs the same suite again.

  That third step is load-bearing. The shortcut is a runtime flag that
  suppresses memory recall during an eval — but that measures a configuration
  nobody can deploy, so "mechanism justified" would be evidence about something
  that doesn't exist. Both arms are real, admitted versions running through the
  ordinary queue and event log.

  The result: does the knowledge base earn its place?

  facts and collapsing them means nobody can enumerate which agents lack a

  Where I deliberately refused to overclaim

  The verdict returns inconclusive below five comparable cases. A 0.1 difference
  over four cases is noise, and reporting it as benefit launders a coin flip
  into evidence that gets cited later. This harness does no significance testing
  — five is a chosen floor, the rationale text says so, and ai-docs/evals.md
  has a "What this does not do" section listing it alongside no variance
  handling (each case runs once) and no shadow traffic routing.

  The llm_judge grader refuses any external model, because §16.1 Constraint 1
  names evals explicitly: "Traces, metrics, evals, and prompt/completion logs
  never leave our perimeter." A judge sends the case input and the completion to
  a model. That refusal makes the judge unusable here — no self-hosted judge is
  registered — and that's the correct failure rather than quietly shipping eval

  Four places I refused the obvious implementation

  Fork tells you what it will break, and refuses by default. A fork resumes
  adapter state and executes forward, so everything the original did after the
  fork point happens again. Nothing in a checkpoint records which side effects
  already fired, so the platform cannot dedupe them — the only honest options
  are to refuse or make the caller say it out loud. GET /fork previews; POST
  refuses when any essential or non_idempotent effect sits past the fork point
  unless acknowledgeDuplicateEffects: true, and the acknowledgement is written
  into the event log with who gave it. Verified live against a run that called
  demo.gated. Read-only and keyed-idempotent effects don't trigger it —
  demanding a flag for those trains people to always pass it.

  Fork rounds the step number down. A run checkpoints at step boundaries, so an
  arbitrary step lands between two; rounding up would resume from state that
  step had never reached.

  Resume won't step past a pending approval. That would execute the action the
  approval gates, which is the §14 control the interaction exists to be. It also
  refuses a leased run rather than creating a second worker the fence would
  reject anyway, and marks the dead letter replayed rather than deleting it —
  §0.8's queue is a ledger.

  PATCH /v1/memory/{id} won't edit content. The embedding was computed from that
  text, so an in-place edit leaves a vector pointing at what the record used to
  say — retrievable by the old meaning, unfindable by the new one. Only
  salience, trusted and expiresAt are amendable; passing content gets the reason
  and a pointer to superseding.

  GET /v1/runs is keyset-paginated on (created_at, id), not OFFSET — a run
  inserted between requests shifts every subsequent page and the caller silently
  misses rows.

  The notify designs differ more than the claim does

  Conductor's is off by default (experimentalQueueNotify = false) and is a hint
  — pollMessages still loops on sleepUninterruptibly(100ms), and a notification
  older than 5s is discarded as stale.

  Its trigger is the part worth knowing about:

  CREATE TRIGGER queue_insert_delete AFTER INSERT OR DELETE ON queue_message
    FOR EACH ROW EXECUTE FUNCTION queue_notify_trigger();

  FOR EACH ROW, and the function aggregates the entire queue_message table
  (GROUP BY queue_name, count(*), min(deliver_on)) to build the payload. Every
  push and every ack pays for a full-queue aggregate — that's the price of
  putting depth and next-delivery inside the notification. Ours is a bare
  pg_notify('run_ready', runId) from application code, fired after commit, as
  the primary wakeup rather than a hint.

  Two structural consequences

  Conductor's queue structurally cannot be transactional with workflow state.
  QueueDAO has five implementations in-tree (Dyno, SQLite, MySQL, Postgres, plus
  SQS/AMQP modules), so it must assume the queue may be a different system —
  which is exactly why it needs a periodic unack sweep. We assume one database,
  which is what buys same-transaction enqueue and epoch fencing. That's the
  tradeoff ADR 0001 recorded deliberately, and this is the concrete thing it
  bought.

  One row per run vs. one row per message. Our PK is run_id, so a run is
  enqueued at most once by construction. And our long waits leave the queue — a
  run suspended on HITL, a peer call or a sub-agent is deleted from run_queue
  and re-enqueued by whatever resolves it, so a week-long wait holds neither a
  worker nor a row. Conductor's equivalent is setUnackTimeout pushing deliver_on
  forward, which keeps the row and re-polls it.

  Where Conductor is ahead

  priority DESC is genuinely in its pop ORDER BY and indexed
  (V7__new_qm_index_desc_priority.sql). Our priority column exists and is in
  run_queue_claimable_idx, but nothing ever sets it — saturation is handled
  upstream at admission by backpressure_policies instead. We're also
  single-pool-per-claim with no fair scheduling across pools, and queuesDetail()
  gives per-queue depth/unacked visibility we only approximate with
  depth(pool).

  That unused priority column is a real loose end — either wire it or drop it,
  since a column nothing writes reads as a feature that exists.

  IndeterminateSideEffect(row.id, row.ref);

  - git push to agent/run-<runId> is naturally idempotent — the second attempt
